# teamPNew 三模式操作流程

本文件约束模式选择、飞书操作与检查范围。模板部署和固定记忆规则见 `memory-contract.md`；不得用本文件的摘要替代随技能附带的完整 `wiki-memory-agent` 内容。

## 共同入口：先选模式，再沿索引找信息

1. 每次引用技能，先请用户选择：**总管理知识库项目**、**新建团队项目**、**检查当前项目与飞书目录是否一致**。若本轮已经明确选择，确认已选模式后直接继续，不重复提问。不得把检查模式自动改为初始化模式。
2. 确认当前项目根目录。仅从已知入口读取现有 `AGENTS.md`、`memory/INDEX.md`，然后沿其明确指向的文件定位信息。允许检查这些已知路径是否存在；不得为寻找记忆递归扫描项目、其他项目或用户磁盘。
3. 按需读取 `memory/project/feishu-context.md`、`memory/project/feishu-catalog.md`、`memory/project/feishu-routes.md` 和 `memory/workflows/route-first.md`。已有索引将它们放在其他明确路径时，以索引为准，记录实际位置，避免再造一套平行记忆。
4. 新电脑、新 AI 工具、新项目**不等于**能共享旧项目的记忆。初始化模式在当前索引不足时，定点读取 `~/.teampnew/INDEX.md` 中匹配的总管理入口（详见记忆契约），也可使用宿主已提供的相关长期记忆线索。仍没有所需信息时，向用户索取总管理项目的**精确索引文件路径**，或可访问的云端目录/项目指南入口；只访问指定入口及其明确路由。路径不可用时说明情况并索取可用入口，不猜测目录、不全盘查找。检查模式不借此跳过本地记忆门槛。
5. 先核对现有信息，再一次性询问当前模式仍缺少的必要项。已有准确记录不重复索取；过期、互相矛盾或无法访问的记录不能视为已验证。
6. 总管理目录 `memory/project/feishu-catalog.md` 才是全局知识库注册与团队默认值的权威来源。团队项目可导入与自身相关的条目、默认值及来源路径/URL，保留导入时间与来源标识；不得将该局部副本宣称为全局最新目录，也不得隐式改写另一个项目。

不要求用户背出飞书内部 token：可以从其提供的 URL 和连接器返回结果解析、补全。无法确定的字段保持未知，不编造 ID、链接、文档正文或成功状态。

## 模式一：建立总管理知识库项目

### 需要确定的信息

- 用户要纳入总管理的全部知识库入口，以及每个入口的用途或范围。
- 各知识库的 `space_id`、入口/父节点及可访问 URL；可从链接与元数据解析。
- 已有的团队项目启动指南、框架指南、模板入口，以及团队产出的默认存放知识库和父节点。用户暂未设定默认值时标记为未设定；后续团队模式再补齐其必要项。

“全部”指用户确认纳入管理的范围。不得通过读取一个入口就声称已经发现账号中的全部知识库，也不得扫描全部空间来猜测遗漏项。

### 执行步骤

1. 从当前路由和可用的总管理索引读取已登记条目，汇总“已有、缺失、待确认”的入口。缺少入口或相关记忆时才索取；已有目录时请用户只补充遗漏或变更。
2. 对每个纳入范围的入口读取必要元数据，确认名称、知识库、节点与位置。只在建立当前目录确有需要时列出指定父节点的直接子项，并处理该层分页；不递归展开整库、不批量读取正文。
3. 以稳定的知识库标识及节点标识去重。入口 URL 变化但指向同一节点时更新记录；多个别名可以保留，不能据此创建重复知识库或重复目录。
4. 按 `memory-contract.md` 部署完整附带模板并合并本项目资料。已有 `AGENTS.md` 时保留它，不另建同名或大小写变体文件、不覆盖既有规则；遵守记忆契约规定的衔接方式。
5. 写入并关联以下文件：
   - `memory/INDEX.md`：明确总管理目录、当前上下文、路由及固定工作流的入口。
   - `memory/project/feishu-context.md`：`project_kind: manager`、管理范围、来源入口及当前完成状态。
   - `memory/project/feishu-catalog.md`：知识库注册、用途、精确入口与已确认的团队指南/模板/产出默认位置。
   - `memory/project/feishu-routes.md`：当前实际纳管的本地或远端路由；不要生成尚未读取的全库文件清单。
   - `memory/workflows/route-first.md`：记忆契约规定的固定路由规则。
6. 回读已更新的索引与本次条目，确认可以从索引直接定位目标。按记忆契约在 `~/.teampnew/INDEX.md` 登记总管理入口，供同电脑的新项目定点复用；无法登记时说明需手动提供入口。交付总管理索引的准确路径，以及未设定、不可访问或仍待补充的字段，供新项目导入。

重复运行时补齐或更新现有注册与索引，不重新初始化已完成的工程，不重复创建飞书节点。

## 模式二：依据指南建立团队项目

### 创建前的必要信息

必须能确定当前项目的启动/框架指南、适用模板（指南明确不需要模板也可）、项目标识或命名方式，以及各类产出的目标知识库和父节点。总管理目录提供的默认值只有在明确适用于当前项目且无冲突时才能采用。

先从当前项目索引找；当前项目缺失时沿已记录的总管理索引精确导入；两者都没有时向用户索取可用的指南入口和目标位置。不能以“应该以前配过”替代当前可访问的证据。多个目标或多份指南冲突时，只询问影响当前创建的具体选择。

### 执行步骤

1. 读取明确定位的启动指南、框架指南和适用模板正文。沿其明确引用且与当前项目有关的链接读取必要补充材料；不要搜索或读取整个知识库。
2. 提取本项目必须产出的文件/文档清单、名称规则、结构、内容要求、顺序及目标父节点。将每项对应到一个稳定 `logical_id`。指南缺少关键项目事实时索取；无法确认的业务事实不得写成既定事实。
3. 验证每个目标父节点的知识库和权限。按目标父节点读取直接子项元数据，并完成必要分页，用节点 ID、已有路由和指南要求的名称检查是否已经存在产出。不得仅凭同名就覆盖不明来源的文档。
4. 先建立或补齐本地记忆工程及可续跑的产出清单，保存已验证指南、模板与目标位置。依照 `memory-contract.md` 部署完整模板并处理已有 `AGENTS.md`，将 `feishu-context.md` 的 `project_kind` 记为 `team`。
5. 依照指南逐项建立、撰写飞书文档。用户选择该模式且提供了明确目标，即可执行其要求范围内的创建与撰写，不额外增加统一审批环节。每完成一个远端对象，立即保存其实际节点 ID、对象 ID、名称、父节点和 URL，随后再进行下一项。
6. 已存在且能由稳定 ID 或明确记录确认属于本项目的产出，应复用并补齐用户授权的内容。目标位置存在同名但身份不明的对象时，记录冲突并请用户作具体选择；不要覆盖、删除或另建一份来绕过冲突。
7. 更新 `memory/INDEX.md`、项目上下文和路由。团队本地的目录资料只收录所需的全局目录引用、导入来源与当前项目相关信息。对没有本地文件的飞书文档使用 `remote` 路由，不为了凑齐映射创建空本地文件。
8. 用返回的实际元数据核对本次产出的名称与位置，并核对指南要求是否已完成。交付文档链接及本地索引路径；明确列出未完成项及其原因。

指南不可访问、模板缺失或目的地不明时，只暂停依赖这些信息的产出。可以整理已知资料和继续不依赖缺失项的部分，不能自行发明一套指南并报告全部完成。

## 模式三：仅检查目录、位置与名称

用户已明确确认：**空项目，或缺少可用的飞书记忆，或无法识别为总管理/团队项目时，停止并提示先初始化；已有完整记忆时，只检查目录位置与文件名称，不对比正文。**

### 先判断是否具备检查条件

1. 仅检查项目根目录的直接条目和上述已知记忆入口是否存在，不做递归文件发现。
2. 沿主索引定位上下文与相关路由，读取 `project_kind`。必须明确为 `manager` 或 `team`，并且存在可用的目标库、父节点及路由记录，足以限定检查范围。
3. 空项目、没有相关记忆、缺失关键路由或类型无法识别时，停止本模式，说明具体缺项并建议选择对应初始化模式。**不得自动部署模板、创建 `AGENTS.md`、建立飞书文档或开始初始化。**
4. 项目类型与路由可用，但某个远端入口暂时无权限、超时或服务不可用时，将该项列为“无法核验”；可以继续检查其他可访问的既定目标，不能将访问失败判为不存在。

### 检查范围与读取方式

- `manager`：检查总管理目录中已登记的知识库入口、已纳管的父节点及明确路由；不因是总管理而扫描所有知识库内容。
- `team`：检查当前团队上下文规定的产出位置及其路由；不扩展到其他团队或整库。
- 本地：读取路由指向的精确路径及必要父目录的直接子项名称。远端：读取明确节点的元数据和纳管父节点的一层子项列表。父子关系需要多级核实时，沿已知祖先 ID 逐级核对，不展开兄弟子树。
- 对选定父节点，处理完该层所有分页后才判定某项未出现在该层；不递归访问子节点。分页中断、返回不全或连接器结果被截断时标记“检查不完整”，不作缺失结论。
- 不读取或比较飞书文档正文、本地业务文件正文、段落、字数、内容摘要、哈希或语义相似度；记忆索引与路由页仍按门槛检查读取。不得为检查一致性导出整个空间。

### 双向核对规则

检查使用 `logical_id` 稳定对应对象，优先核对节点/对象 ID，再核对当前实际名称和父节点位置。

| 路由类型 | 应核对什么 | 不应判为什么 |
| --- | --- | --- |
| `local` | 本地精确路径、名称及所在目录 | 没有远端副本不算缺失 |
| `remote` | 飞书节点名称、知识库及父节点位置 | 没有本地文件不算缺失 |
| `paired` | 两端各自应有的名称/位置和既定映射 | 不要求本地文件名与飞书标题字面完全相同，除非路由明确如此规定 |

执行两类比较，不能只确认“记忆里的对象存在”就宣称一致：

1. **从记忆到实际目录**：逐条核对纳管路由是否可见、是否在预期父节点、名称是否匹配。相同稳定 ID 的对象改名或移动，分别记为名称差异、位置差异；不要误报为旧对象丢失并新建。
2. **从实际目录到记忆**：对已明确纳管的本地父目录与远端父节点，比较直接子项与路由集合，找出范围内的未登记项、同名冲突或重复映射。若只纳管其中一部分，必须使用记录的范围规则；其他业务对象不能一概当成多余文件，更不能据此删除。

不能在已知范围确认对象当前位置时，报告“原位置未见，当前位置未确认”。禁止为了寻找移动后的对象进行全库或全盘扫描。只有连接器明确且可靠地返回对象不存在或删除状态，或者完整且有权限的既定目录检查确实证明其未出现在该位置，才能作对应范围的缺失判断；后者不等于证明对象已全局删除。

### 检查结果

结果至少注明：项目类型、检查的父目录/父节点、分页是否完成、每项差异的 `logical_id`、预期与实际名称/位置、证据及无法核验原因。按“一致、名称差异、位置差异、原位置未见、未登记项、映射冲突、无法核验”分类；只对全部检查完成且没有差异的范围称为一致。

该模式不创建、删除、改名、移动或重写业务文件和飞书文档。可以把核验时间、检查范围、差异和未完成状态记入已有记忆；不要把预期路由悄悄改成现状来消除差异。需要调整业务对象或确认预期方向时，列出明确的下一步，待用户提出相应修改请求后执行。

## 幂等、失败与续跑

- 所有模式使用已有稳定 ID 和精确路由续跑，不以标题相似或前次自然语言总结猜测对象身份。
- 远端创建前保存当前意图及目标父节点，创建成功后立即保存返回的实际 ID。创建请求超时或结果不确定时，先在原目标父节点的一层元数据中核实结果，再决定是否重试；不得盲目再次创建。
- 本次未完成的步骤记录明确状态与阻塞原因。`verified_at` 只记录实际完成核验的时间；无权限、超时、未执行不填成成功核验。
- 新增、删除、改名或移动实际发生后，立即同步受影响路由及其上级索引。操作结果不确定时先保留未确认状态，不能把计划写成已完成。
- 若目录较大，按明确父节点或业务范围拆分路由文件，并在主索引维护精确入口。每轮后续任务先匹配路由中的目录、位置和名称，再访问必要文件；禁止以任务复杂为由退回全扫描。
