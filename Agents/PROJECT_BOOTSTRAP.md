# 新项目一键启动协议

> 本文件是一份交给 AI 执行的项目初始化指令，不是项目自身的 `AGENTS.md`。
> 收到本文件后，AI 必须按照以下流程创建一个新项目文件夹，并在其中生成正式的 `AGENTS.md`。

## 目标

根据用户在当前对话中提供的需求、附件和约束：

1. 确认项目的必要信息。
2. 创建一个独立的新项目文件夹。
3. 在新文件夹根目录生成适合该项目的标准 `AGENTS.md`。
4. 验证交付结果并向用户汇报。

默认只创建项目文件夹和其中的 `AGENTS.md`。除非用户明确要求，否则不要生成业务代码、安装依赖、初始化 Git、提交代码、部署项目或调用会产生外部副作用的服务。

## 执行原则

- 将用户当前对话中的明确要求视为项目事实；本文件只定义执行流程，不替代具体项目需求。
- 先检查当前工作目录、用户附件和已有文件，再决定需要询问什么；不要重复询问已经能够可靠确定的信息。
- 不得猜测项目名称、核心目标、保存位置、技术栈、命令、路径或业务规则。
- 缺少会影响目录创建或 `AGENTS.md` 内容的关键信息时，必须先向用户提问，收到回答后再继续。
- 问题应尽量合并成一轮、数量最少且便于回答；不要为无关细节阻塞初始化。
- 可以依据用户目标提出建议，但必须把“用户已确认的事实”和“AI 的建议”明确区分。
- 所有文件使用 UTF-8 编码；不得写入密码、令牌、API Key、私钥或真实敏感数据。
- 保留用户已有文件，不覆盖、移动或删除与本次初始化无关的内容。

## 第一步：提取并确认需求

先从当前对话和附件中提取以下信息：

- 项目名称。
- 项目要解决的问题、主要用户和预期成果。
- 新项目文件夹的保存位置。
- 项目类型和当前阶段，例如网站、桌面应用、脚本、数据分析、文档项目或原型。
- 已明确的技术栈、运行环境、平台限制和版本要求。
- 已明确的目录结构、开发命令、测试方式、编码规范和安全边界。
- AI 可以自主执行的操作，以及必须先获得用户确认的操作。
- 用户要求创建的额外交付物；未明确要求时仅交付 `AGENTS.md`。

以下三项是创建前的最低必要信息：

1. 项目名称。
2. 项目核心目标。
3. 项目文件夹的保存位置。

如果其中任一项无法从上下文可靠确定，先询问用户。技术栈不是创建文件夹的必填项；用户尚未决定时，可以在正式 `AGENTS.md` 中明确写为“尚未确定”，但不得虚构技术选择或可执行命令。

当用户的名称或路径包含非法字符、指向现有非空目录、可能覆盖文件，或存在多个合理解释时，必须说明具体问题并请求用户确认新的名称或位置。

## 第二步：制定初始化方案

信息足够后，先在内部整理以下结果，然后直接执行；除非存在高风险歧义，否则不需要再次请求批准：

- 新项目文件夹的绝对路径。
- 从用户需求得出的项目边界。
- 应写入项目 `AGENTS.md` 的已确认事实。
- 当前未知、因此需要省略或明确标记为尚未确定的事项。

路径处理规则：

- 优先使用用户明确指定的保存位置和项目文件夹名称。
- 创建前检查目标路径是否存在。
- 目标路径不存在时，创建该文件夹。
- 目标路径为空目录时，可以在用户意图明确的情况下使用。
- 目标路径为非空目录时，不得把它当成“新项目”直接写入；必须先请求用户选择新目录或明确授权使用现有目录。
- 不得使用会覆盖已有文件的强制参数或破坏性命令。

## 第三步：生成项目级 `AGENTS.md`

在新项目文件夹根目录创建且只创建一个名为 `AGENTS.md` 的项目指令文件。文件必须是针对当前项目的成品，不得复制本启动协议，也不得保留未填写标记、`TODO`、示例值或其他占位符。

### 内容要求

根据项目实际情况选择以下章节。仅保留有真实信息或对后续工作确有价值的章节，不要为了凑齐结构而添加空章节。

1. `# AGENTS.md`
2. `## 项目概览`
   - 项目名称、核心目标、主要用户、当前阶段和交付边界。
3. `## 项目结构`
   - 已存在或已经明确规划的关键路径及用途。
   - 新项目尚无源码时，明确说明当前只有初始化文件，不虚构目录。
4. `## 环境与命令`
   - 只写已经确认且能够执行的安装、开发、构建、格式化、检查和测试命令。
   - 尚无工具链时，写明“当前尚未确定工具链和可执行命令；建立项目骨架后必须更新本节”。
5. `## 开发规范`
   - 已确认的语言版本、格式、命名、类型、错误处理、日志、文档和依赖边界。
6. `## 工作流程`
   - 开始任务前检查相关文件和工作区状态。
   - 保留用户已有修改，只处理当前任务范围。
   - 实施最小且完整的改动，避免无关重构和依赖升级。
   - 修改后执行与风险相匹配的验证。
7. `## 测试与完成标准`
   - 根据项目类型定义可执行的验证要求。
   - 无法执行检查时，要求说明未执行项、原因和建议验证方式。
8. `## 安全与权限边界`
   - 禁止写入密钥和真实敏感数据。
   - 未经用户明确授权，不得删除重要数据、覆盖文件、重写共享 Git 历史、执行不可逆迁移或产生外部副作用。
   - 根据用户要求写明新增依赖、修改公开接口、部署、付费操作等是否需要确认。
9. `## 沟通与交付`
   - 使用用户指定的沟通语言；未指定时沿用用户当前使用的语言。
   - 最终汇报必须包含结果、关键文件、验证情况和剩余风险。
10. `## Git 约定`
    - 仅在用户已经给出 Git 工作流要求时添加。
    - 未经用户明确要求，不自动提交、推送、创建 Pull Request 或合并分支。

### 编写标准

- 使用普通 Markdown，不添加无必要的 YAML frontmatter。
- 规则应简洁、明确、可执行、可验证；一条规则只表达一个主要要求。
- 路径、文件名、命令和配置项使用反引号标记。
- 只记录需要跨任务持续生效的项目事实和规则，不记录一次性聊天内容。
- 优先写 AI 无法仅从代码可靠推断出的业务约束、权限边界和验收条件。
- 禁止事项应同时说明安全替代方案或需要用户确认的条件。
- 不引用并不存在的文件、目录、脚本或命令。
- 避免重复通用常识；根目录 `AGENTS.md` 应保持精简，通常控制在约 200 行以内。
- 如未来存在不同模块的特殊规则，可以在相应子目录增加 `AGENTS.md` 或 `AGENTS.override.md`，根文件只保留全局规则。

## 第四步：验证

创建完成后，必须进行以下检查：

- 新项目文件夹位于用户确认的位置。
- 文件夹名称与用户确认的项目名称一致，或已说明必要的安全化处理。
- 根目录存在且仅存在本次获准创建的文件；默认应只有 `AGENTS.md`。
- 文件名严格为 `AGENTS.md`，大小写正确。
- 文件可按 UTF-8 正常读取。
- 内容与用户需求一致，没有占位符、虚构路径、虚构命令或敏感信息。
- 所有写入操作均限制在用户确认的新项目文件夹中。

若任何检查失败，先修正问题并重新检查；无法修正时，停止扩展操作并向用户说明阻塞原因。

## 第五步：交付汇报

完成后向用户简洁说明：

- 已创建的项目文件夹绝对路径。
- 已生成的 `AGENTS.md` 绝对路径。
- `AGENTS.md` 覆盖的主要规则。
- 已完成的验证。
- 尚未确定、需要在项目开始开发后补充的内容。

如果因为缺少最低必要信息而尚未创建文件夹，只提出需要用户回答的问题，不得声称初始化已经完成。
